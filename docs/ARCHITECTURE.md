# 架构说明

## 模块

- `engine/TransformEngine`：共享规则引擎，预览与服务均使用此引擎。
- `engine/MappedText`：记录转换结果的每个 UTF-16 单元对应的原文范围。
- `engine/ChatDraft`：当前输入框的原文、用户编辑、字面片段和稳定后缀选择。
- `service/ChatTargets`：QQ 与 Discord 的聊天输入框识别。
- `service/MoeAccessibilityService`：事件调度、输入框读取、组合输入检测、写回与校验。
- `data/`：配置持久化、预设和有大小限制的文本读取。
- `engine/BidiTools`：独立的 QQ Unicode 昵称与正文保护工具。

## 输入过程

无障碍事件通知间隔为 0。输入、焦点、选区和窗口内容变化触发主线程队列任务，
同一轮队列中的多个事件合并，读取输入框的最新快照。

输入时立即执行替换。停顿模式在原文最后变化 120 毫秒后完成消息装饰；
实时模式在非组合输入状态下直接完成装饰。无需等待发送点击，也不操作发送按钮。

输入后最多 1.8 秒内，每 100 毫秒补充检查一次；组合输入时采用 60 毫秒间隔。
离开目标应用后取消任务。输入框暂时不可用或写回失败时最多延迟重试三次，
间隔为 40、80、120 毫秒。文本及配置未变化时复用结果，不重复计算或随机抽取。

## 编辑与来源映射

每次变换保留结果到原文的范围映射。收到新文本后，比较共同前后缀，将编辑投影回原文。
在已展开替换词内部的修改扩展到整个来源片段，保留用户编辑后的字面文字。
其他部分继续正常转换，不再暂停整条消息，也不从全局字串猜测并删除后缀。

例如，「我」转换为「本喵」后继续输入「们」，原文仍能恢复为「我们」；
将「谢谢啦」手动删为「谢谢」后，该手动修改保留，新输入的其他文字继续转换。
用户主动修改生成的装饰时，本条消息停止自动补回装饰，但继续执行普通替换。

每条消息固定随机后缀和颜文字。清空输入框后推进顺序选择。
焦点短暂离开时保留当前编辑器映射；绑定到不同编辑器时重置。
写回成功后把原选区映射到新文本，末尾光标置于生成装饰之前以便继续输入。

## 平台适配与写回

QQ 使用聊天输入框资源 ID；Discord 使用聊天输入框 ID 或消息输入提示，
排除搜索框。定位只读取当前窗口的输入焦点，不递归扫描聊天消息列表。

写回前重新检查应用、输入框、焦点、原文、选区和组合输入状态。
使用 ACTION_SET_TEXT，读取完整结果校验，不使用剪贴板回退。
检测到组合输入时延后写入。检测到特殊提及或替换组件的富文本时保留原样。

Discord 提示和 ID 的适配目前经过逻辑测试，尚无真实客户端节点树验证。
无障碍快照可能不暴露全部组合输入或提及信息；真实客户端兼容性需持续验证。

## Unicode 工具

BidiTools 保持独立，不参与聊天平台自动改字适配。昵称模板使用 RLI、LRO 与嵌套 RLI；
正文保护闭合未结束作用域，并按段落使用 LRI/PDI 包裹正文。
加强模式额外追加三组 PDI/PDF。预览使用本机文本排版，保持现有 QQ 用途。
